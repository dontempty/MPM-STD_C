# FFT_test — FFTU 기반 압력 Poisson 솔버와 기존 솔버 비교 (2026-11-06)

## 0. 결론

GPU 만 본다. GPU 당 512³ weak 측정, GPU 64 장까지, z tanh 스트레칭.

- **정확도**: 전 구성 PASS. 두 솔버의 해 차이는 최대 2.8e-12 (상대).
- **속도**: GPU 1·2 장은 같고, GPU 4 장 이상은 FFTU 가 **1.56~1.97 배 느리다**.
- **이유**: 장이 블록 분배라 FFTU 도 기존 전치와 같은 재분배가 필요하고, 그 위에 FFTU all-to-all 2 회가 더 붙는다. GPU 64 장에서 +73 ms 인데 z TDMA 통신 절감은 −13 ms 다.
- **권고**: 압력 솔버는 기존 평면묶음 경로를 유지한다. 기존 소스 변경은 0 건이다.
- **통신 방식 (§11)**: x 를 나누지 않은 격자의 펜슬 경로에서 x·y 전치를 pairwise 로 바꾸면 총시간이 GPU 32 장 22~24 %, 64 장 33~36 % 준다. NCCL 은 전치만 빨라지고 총시간은 개선되지 않는다.
- **cube 분할 (§12)**: 평면묶음이 펜슬보다 항상 빠르다 (GPU 256 장까지). 평면묶음 + pairwise 는 GPU 32~256 장에서 약 30 % 빠르고, GPU 16 장에서는 10 % 느리다. z TDMA 의 pairwise 는 이득이 없다.

표·그림: `plot/weak_512_v2_*`. 만드는 법은 §7.

## 1. 논문 알고리즘

Koopman & Bisseling (2023), SIAM J. Sci. Comput. 45(6) C330, `/scratch/t525a06/KDH/FFT/paper/22m1487242.pdf`.

순환 분배에서 로컬 FFT → 트위들 + 패킹 → all-to-all 1 회 → 작은 FFT. 조건은 p_l² | n_l, 입력·출력 분배가 같다. all-to-all 은 **변환 1 번당 1 회**다. 입력이 이미 순환 분배라는 것이 전제이고, 논문의 이득은 입·출력 분배가 같아야 할 때 추가 재분배를 없애는 데서 나온다. 분배가 달라도 되면 FFTW·PFFT 와 비슷하다고 논문이 보고한다.

## 2. 기존 솔버 (`src/equation/pressure/`, 수정 없음)

x r2c + y c2c + 모드별 z PaScaL TDMA. 슬랩(npx = npy = 1)은 전치가 없고, 평면묶음(npx·npy > 1 기본)은 그룹 전치 2 회 뒤 x·y FFT 가 통신 없이 끝나며 z 사슬은 전체 랭크다. `Solver::timer` 와 `comm_seconds` 로 단계별 시간과 MPI 시간을 읽는다.

## 3. 설계 (v2)

사용자 결정: z 스트레칭 사용 (전 방향 스펙트럴 제외), GPU 64 장까지, `rbc_nob_scalability` 와 같은 방식 (`normal`, GH200 4 GPU/노드, 1 랭크 = 1 GPU).

```
rhs 블록 ─재분배─▶ y 순환 x 라인 ─ x r2c ─ 재배열 ─ y 로컬 FFT ─ 트위들+패킹 ─ all-to-all ─ 언팩 ─ 작은 q 점 FFT ─▶ 스펙트럼
   ─ 모드별 z TDMA (기존 밴드 식, 원래 z 통신자) ─▶ 위의 정확한 역순 ─재분배─▶ phi 내부 → halo + z 벽 ghost
```

- x 는 분배하지 않고 r2c 로 변환한다 (Alg 2.3 의 p1 = 1). 시스템 수가 기존과 정확히 같다. q = npx·npy, 조건 q² | ny.
- 게이지·핀·고유값은 기존과 같고, 기존 밴드 조립·재배열·핀·DC 합 함수를 호출만 한다.
- 재분배는 기존 평면 전치와 같은 타일 전치 + 행 복사다. 자기 몫은 `MPI_Alltoallv` 에서 빼고 디바이스 복사로 처리한다 (GTL 의 디바이스 self 전송이 느린 문제).
- q = 1 이면 FFTU 단계와 MPI 를 건너뛴다 (기존 슬랩 경로와 같은 연산).
- 슬롯 4 개를 수명이 겹치지 않는 버퍼끼리 나눠 쓴다 (`cyclic_fft.hpp`).

### v1 에서 고친 것

v1 (x·y 2 차원 순환 + c2c) 은 해는 맞았지만 같아야 할 계산이 느렸다. 원본은 `results/v1_source_20261106.tar.gz`.

| 재분배 인덱스 표 | 팩·언팩 10.8 ms (기존 3 ms) | 타일 전치 |

### 읽을 때 주의할 점

- **할당 차이**: np 마다 잡이 하나라 weak 곡선 모양은 그 할당의 노드 배치를 탄다. 같은 기존 솔버가 np 16 에서 v1 잡 51 ms, v2 잡 83 ms 였다. 같은 잡 안의 두 솔버 비교는 유효하다.
- **평균 제거 + halo 의 차이**: 같은 일인데 FFTU 쪽이 크다. 앞 단계에서 늦은 랭크를 MPI 에서 기다리는 시간으로 추정하지만 검증하지 않았다.
- **self 전송**: 코드를 점검한 결과 실행되는 GPU 경로는 모두 우회한다. 남은 잠재 경로는 `subdomain_halo.cu` z 방향 하나다 (z 주기 + npz = 1, 그런 덱은 없다). 기존 소스라 고치지 않았다.
- **간헐적 멈춤**: v1 의 np 64 첫 런이 15 분 멈췄다가 다음 런은 72 초에 끝났다. v2 는 np 64 3 런 모두 정상이다. 재현되지 않았을 뿐 원인은 모른다. 다시 멈추면 로그의 마지막 `# stage` 가 위치를 알려 준다.

## 10. CaNS·PaScaL 과 같은 문제로 비교 (GPU 64 장까지)

패키지: `/scratch/t525a06/KDH/CaNS_vs_PaScaL_Hangang_GH200_NP256_3STEP` (이미 빌드된 실행파일과 입력 생성기를 읽기만 한다).

- **문제**: `COMPARISON_CONTRACT_HANGANG.md` 그대로. 균일 격자, x·y 주기, z Neumann, φ = cos πx cos πy cos πz, rhs = −3π²φ. `weak256` (GPU 당 256³) 와 `strong1024`.
- **프로세스 격자**: 1×np2×np3 (x 를 나누지 않음). 비교 계약이 np1 = 1 로 고정해 cube 는 이 비교에 없다 (CaNS 는 x-펜슬 입력, PaScaL 소스에는 np1 > 1 의 cube → x-펜슬 경로가 있지만 실행해 보지 않았다).
- **측정**: 한 잡 안에서 번갈아 실행, 예열 5 + 측정 20, 풀이별 rank-max 의 평균, 3 회 중앙값. CaNS·PaScaL 은 프로파일 없이 총시간과 RMS 만 (사용자 결정). event 분해는 MPM-STD·FFTU 만.
- **정확도**: 5 개 방법의 RMS 가 해석값과 일치한다 (`weak256` 1.774870e-5, `strong1024` 1.109262e-6, 방법 간 상대 차 ≤ 3.4e-8).

해석:

- **GPU 16 장까지**: MPM-STD 가 가장 빠르거나 PaScaL 과 비슷하다. CaNS 보다 빠르다. 빌드가 다르므로 (CUDA 12.9 대 12.8) GPU 1 장의 차이에는 그 영향이 섞여 있을 수 있다.
- **GPU 32 장부터**: PaScaL 이 앞선다 (MPM 최선 대비 weak 25 %, strong 21~29 % 빠름).
- **펜슬 대 평면묶음**: x 를 나누지 않으면 GPU 32 장부터 펜슬이 빠르다. z 사슬이 짧아 z 풀이가 절반이다 (weak256 np 64: 2.44 대 4.75 ms). cube `4x4x4` 는 반대다 (§6 절 이전 측정: 펜슬 180, 평면묶음 113 ms).
- **FFTU**: 분배가 있는 구간에서 항상 가장 느리다. 전치 + FFTU all-to-all 로 x·y 통신이 평면묶음의 2 배다.
- **GPU 32 장 차이의 원인 → §11 에서 시험**: 처음에는 `MPI_Alltoallv` 대 point-to-point 의 차이로 보았으나 그 가설은 틀렸다 (FFTU 시험에서 p2p ≈ Alltoallv). 차이를 줄인 것은 상대별로 차례를 두는 pairwise 다.

## 11. 통신 방식 비교 (MPM-STD 펜슬 경로, GPU 64 장까지)

- **바꾼 것**: 펜슬 경로의 x·y 전치만. 기존 소스를 고치지 않고 `transpose_transport.*` 가 `MPI_Alltoallv` 를 PMPI 로 가로챈다 (`FFT_TEST_TRANSPOSE=alltoallv|pairwise|nccl`). z TDMA·halo 는 모든 방식에서 MPI 다.
- **pairwise**: i 번째 차례에 (나 + i) 로 보내고 (나 − i) 에서 받은 뒤 끝날 때까지 기다린다. **NCCL**: 같은 쌍을 `ncclGroupStart/End` 로 묶는다. 2.25.1, `NCCL_PROTO=^LL128`, 멀티노드는 `aws-ofi-nccl/1.20.0` (로그에 `Selected provider is cxi` 확인, NCCL WARN 0).
- **측정**: §10 과 같은 계약 (1×np2×np3, 균일 z, 예열 5 + 측정 20, rank-max 평균, 3 회 중앙값). np 마다 한 잡 안에서 방식과 PaScaL 을 번갈아 실행. 전 런 RMS 가 해석값과 일치한다. 잡 1229622 (np 4), 1229589 (np 8), 1229623 (np 16), 1229624 (np 32), 1229625 (np 64), 실패 0.

해석:

- **pairwise**: 대 Alltoallv 로 GPU 32 장 −22~−24 %, 64 장 −33~−36 %. GPU 4·8 장은 같다 (상대가 1 개라 차례를 나눌 게 없다). GPU 16 장은 +3~+6 % 로 오히려 조금 손해다.
- **P 만으로 정해지지 않는다**: np 16 과 np 32 는 둘 다 P = 4 인데 Alltoallv 전치는 4.51 → 6.33 ms 로 늘고 pairwise 는 4.65 → 4.67 ms 로 평평하다. 원인은 확인하지 않았다.
- **랭크 간 편차**: weak256 np 64 전치의 랭크별 범위는 Alltoallv 7.41~9.15, pairwise 5.57~5.64 ms 다. z TDMA·평균 제거·halo 도 pairwise 에서 작아지는데 (1.38 → 0.48 ms), 다른 랭크를 덜 기다리는 효과와 맞는 방향이다. 직접 분리해 재지는 않았다.
- **대 PaScaL**: GPU 64 장은 pairwise 가 앞선다 (8.60 대 10.60, 8.36 대 10.05). GPU 32 장은 PaScaL 이 약간 앞선다 (weak +2 %, strong +9 %). GPU 4~16 장 strong 도 PaScaL 이 5~8 % 앞선다. PaScaL 은 정적 TDMA 인수와 CUDA 12.8 빌드라 통신만의 차이는 아니다.
- **NCCL**: 전치는 GPU 64 장에서 Alltoallv 대비 −28~−29 % 지만 pairwise 에는 못 미치고, GPU 8 장에서는 크게 느리다. 총시간은 나아지지 않는다 (rank-max 기준 대 Alltoallv: np 8 +31~+35 %, np 32 +12 %·−4 %, np 64 +4~+6 %).
  - 첫째 이유: z TDMA + 평균 제거 + halo 가 커진다. np 64 에서 weak 1.38 → 3.76, strong 1.48 → 3.64 ms. 전치 이득 2.3~2.5 ms 를 거의 상쇄한다.
  - 둘째 이유: 랭크 편차. np 64 에서 rank-max 와 랭크 평균의 차이가 NCCL 1.5~1.7 ms, pairwise 0.05 ms 안쪽이다. 랭크 평균으로 보면 NCCL 은 Alltoallv 보다 4~5 % 빠르다 (12.00 대 12.59, 12.09 대 12.66).
  - z·halo 가 커진 원인은 미검증이다. `aws-ofi-nccl` 모듈이 `FI_CXI_RDZV_THRESHOLD=0`, `FI_CXI_RDZV_EAGER_SIZE=0` 등을 설정해 같은 프로세스의 MPI 에도 걸리는 것이 후보이고, 대기 시간일 수도 있다. Alltoallv·pairwise 를 이 모듈을 켠 채 돌리면 잡 1 개로 가를 수 있다.

읽을 때 주의:

- **구성은 따로 돈 단계 패스다**: 경계마다 `cudaDeviceSynchronize` 가 들어간다. 같은 정의(랭크 평균)로 타이머 없는 패스와 비교하면 4 % 안에서 맞고, 예외는 strong1024 np 8 NCCL 이다 (70.8 대 57.5 ms, 3 회 모두, 원인 미확인). 이 런의 전치 43 ms 는 과대치이며 타이머 없는 패스에서 통신 전체가 41 ms 다. 그래도 MPI 28 ms 보다 크다. 구성 그림의 검은 눈금이 타이머 없는 패스 값이다.
- **Alltoallv r2 (strong1024 np 8)** 의 단계 패스 한 번도 z·halo 가 튀었다 (54.9 ms). 중앙값에서 빠진다.
- **격자**: 1×np2×np3 에서만 쟀다. cube 분할과 평면묶음 경로는 §12 에서 쟀다.
- **할당**: np 마다 잡 1 개다. 할당이 바뀌면 같은 코드도 달라진 적이 있어 (§6) 같은 np 안의 비교가 np 사이 비교보다 믿을 만하다.
- **NCCL**: 1 노드에서는 플러그인 도메인 생성이 실패해 (RC −38) np 4 만 플러그인 없이 돌렸다. VNI 부재로 보이나 확인하지 않았다. NCCL 2.25.1 은 CUDA 12.8 빌드인데 실행은 CUDA 12.9 다.
- **`docs/Scalability/pressure_scalability_analysis_20261106.md`** 의 "MPI 튜닝으로 전치를 줄일 수 없다" 는 펜슬 경로에서는 이 측정과 어긋난다. 그 문서의 평면묶음 경로는 재지 않았다. 문서는 고치지 않았다.
