# rbc_nob ΔT=60 div 스파이크 — 원인 추적 (2026-10-05) → 수정 적용 (2026-10-06)

## 증상

fig9 캠페인 dt60 런(128×128×256, 잡 35487, gpu01)에서 투영 후 max|div| 가
평상시 1e-13 인데 **모니터 지점의 ~10%에서 1e-6 급으로 튄다** (최대 5.6e-6,
서서히 증가 추세). 발산 가드(1e3)까지는 멀지만 "터질랑 말랑"으로 보이는 수준.
dt40 런은 같은 격자에서 max 1.3e-9 로 깨끗했다.

```
우리 dt40 (128²x256)   med=3.7e-14  max=1.3e-9   >1e-6: 0%
우리 dt60 (128²x256)   med=1.9e-13  max=5.6e-6   >1e-6: 10.3%   ← 문제
```

## 기각된 가설: 해상도/dt

처음에는 "참조 캠페인의 ΔT=20·60(p8/p9)은 256²×256 인데 우리는 128² 복제라
dx 2배→dt 2배(0.0050 vs 0.0026)로 NOB 안정성 경계(dt≤0.005)에서 운전 중"
이라고 진단했다. 그러나 **원본(MPM-STD_C)의 `reorder_cold_dt60` 런이
완전히 같은 조건**(128×128×256, γ_z=2.6, ΔT=60, CFL 0.3, dt 중앙값 0.0050
동일)에서 **div max 3.5e-12 로 깨끗**함을 확인 — 해상도·dt 가설 기각.

```
원본 reorder_cold_dt60 (같은 128²x256, 같은 dt)  med=1.5e-13  max=3.5e-12
원본 p9 (256²x256, dt 0.0026)                    med=2.5e-14  max=3.2e-11
```

div 정의는 두 코드가 동일(같은 식·같은 메트릭)함을 확인 — 절대값 비교 유효.

## 유력 원인: 투영 직전 물성 재갱신 누락 (포팅 차이)

원본 GPU 경로(`MPM-STD_C/apps/rbc/main.cpp:307-310`)의 스텝 순서:

```
update_properties(Tⁿ) → scalar → Tⁿ⁺¹ → buoyancy·momentum (물성 Tⁿ)
→ update_properties(Tⁿ⁺¹)   ← "Update CPU properties for pressure"
→ pressure/projection        ← 1/ρ̂ 가 Tⁿ⁺¹ 기준
```

우리 포팅(`apps/rbc_nob/main.cpp`)은 스텝 시작에 한 번만 갱신해서 **투영
(ExtraTerm + correct_velocity_variable)이 Tⁿ 의 낡은 1/ρ̂ 로 돈다.**
NOB 근사 투영의 잔차 div 는 ∂(1/ρ̂)/∂t 에 비례하므로 이 가설은 관측 패턴을
전부 설명한다:
- ΔT=60 에서만 심함 (ρ̂(T) 민감도 최대) — dt40 은 1000배 작은 같은 기전
- 플룸 이벤트에서만 튀고 평상시 중앙값은 원본과 동일 (T 변화가 느리면 무해)
- 같은 dt 의 원본 런은 깨끗 (재갱신이 있으니까)

## 수정과 검증 (진행 중)

- 수정: `apps/rbc_nob/main.cpp` 투영 블록 직전에
  `physics::update_properties(properties, T, model, sub);` 1줄 추가 (원본 1:1).
- 빌드 분리: `build_gpu_fix/` (수정) vs `build_gpu_m11/` (미수정 — 돌고 있는
  dt20/dt60 프로덕션이 쓰는 바이너리라 건드리지 않음).
- A/B: 프로덕션 dt60 의 체크포인트(step 3,050,000, t=15300.77 — 사본
  `tmp_nob_ab/ck_base.bin`)에서 두 바이너리로 **같은 40,000스텝 창**을 재생해
  div 통계 비교. gpu02 홀더(35486) 안에서 실행 (dt20 과 공유라 ~2배 느림).
- 판정 기준: fix 판에서 div>1e-7 스파이크가 사라지고 max 가 1e-11 급으로
  내려오면 확정.
