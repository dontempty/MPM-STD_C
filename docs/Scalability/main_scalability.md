# rbc_nob 전체 스텝 측정 — 어디에 시간이 가는가 (2026-10-17)

`apps/rbc_nob/main.cpp` 의 시간 루프를 호출 단위 17 구간으로 재고(plan.md §1·§2), 256³·512³ strong / weak 를 1노드 np ≤ 4 로 돌렸다.
200 스텝 중 워밍업 50 제외, 반복 2–3회 중 step_total 중앙값 런. 단위 ms/step(랭크 max). 수치 게이트: np·하드웨어에 무관하게 모니터 값 동일.

## 2g. np 8 의 PaScaL Alltoallv — 경로 측정 (2026-10-18, "4번")

np 8 strong 256³ 에서 분산 TDMA 의 축소계 Alltoallv 가 스텝의 1/3 (momentum 5.5 + scalar 1.9 + pressure 1.9 ms). 코드를 바꾸기 전에 **전송 경로가 한계인지** 쟀다.
풀이 한 번의 통신 = 앞으로 a′·c′·d′ 3배열 × 경계 2행 (랭크당 3.1 MB, 상대마다 390 KB) Alltoallv 1회 + 뒤로 d 1배열(1.0 MB) 1회 — 이미 한 버퍼에 묶여 있어 횟수는 줄일 수 없다
(세 성분 풀이는 커플링 때문에 순차). `diag/alltoall_bw.cu`(같은 크기의 순수 MPI Alltoallv, gpu02 V100 8장)와 솔버 `PASCAL_TDMA_MPI_MODE=host` 런(`v100hst`).

| 순수 MPI Alltoallv, 3.1 MB/랭크 (256² 시스템) | 디바이스 버퍼 | 호스트 경유(D2H + 호스트 Alltoallv + H2D) |
|---|---|---|
| np 2 (NVLink 쌍) | 0.085 ms (**37 GB/s**/랭크) | 1.13 ms |
| np 4, 한 소켓 (0,1,2,3) | 0.35 ms (8.9 GB/s) | 1.39 ms |
| np 4, 소켓 사이 (0,1,4,5) | 0.44 ms (7.1 GB/s) | 1.35 ms |
| **np 8** | **1.66 ms (1.9 GB/s)** | 1.41 ms (2.2 GB/s) |
| np 8, UCX_TLS=cuda_ipc,… / RNDV=get_zcopy | 1.61 / 1.57 ms | — |
| 512² 시스템(12.6 MB), np 8 | 6.8 ms (1.9 GB/s) | 6.7 ms |

- 솔버 안의 값(풀이당 1.84 ms = 5.5/3)은 벤치의 앞(1.66) + 뒤(0.60) 합과 같다 → **PaScaL 구현의 손실이 아니라 MPI Alltoallv 자체의 한계**.
- 쌍 하나는 빠르다(소켓 사이 4랭크도 7 GB/s). np 8 에서만 1.9 GB/s 로 떨어지는 것은 **28쌍 중 16쌍이 동시에 소켓 사이 링크를 나눠 쓰기 때문**: 소켓 사이로 흐르는 총량 12.6 MB/방향 ÷ 1.66 ms ≈ 7.6 GB/s = 그 링크(PCIe·QPI, 호스트 메모리 경유)의 합계 한계. UCX 설정은 효과 없음.
- 호스트 경유는 벤치에서 15 % 빠르지만 복사 2회가 추가되어 **솔버에서는 2배 느림**(tdma_comm 5.5 → 10.3 ms, 스텝 28.6 → 37.8): 기본(device) 유지.
- 따라서 z-슬랩 np 8 의 Alltoallv 는 노드 토폴로지의 한계이고, 코드로 줄일 수 있는 것은 **소켓 사이를 건너는 바이트 수**뿐이다. 이는 바로 **3차원 분할**이 해결한다: 2×2×2 면 축마다 Alltoallv 상대가 1개(NVLink 쌍, 37 GB/s)라 같은 바이트를 20배 빠르게 보낸다.
  z-슬랩에 남아서 할 수 있는 것은 2단계 축소계(소켓 안 Alltoallv → 소켓 대표끼리 교환)뿐인데 PaScaL 알고리즘 변경이라 **하지 않는다**.
- 부수: 팩·언팩이 상대·배열마다 커널을 띄워 풀이당 64회(np 8). 통신이 아니라 tdma_z 계산 쪽 0.2~0.3 ms — 작은 항목으로 남겨 둔다.

## 2h. pressure_solve 분해 (2026-10-18) — 재배열·팩·산포가 전치 복사

`pressure::Solver::timer` 로 14단계를 쟀다 (꼬리표 `v100q`, 바이너리 = `v100p` + 타이머). V100 256³ np 1 pressure_solve 13.4 ms:

| 단계 | ms | 비중 | 무엇 |
|---|---|---|---|
| **reorder_x_to_y** | **4.31** | 32 % | x 스펙트럼 [(jy·nz+k)·Nxm+mx] → y 배치 [(k·Nxm+mx)·Ny+jy] 복사. 스레드가 mx 를 걸어 **쓰기가 Ny 보폭** |

| reorder_y_to_x | 1.25 | 9 % | 역방향 — 읽기가 보폭 (쓰기 보폭보다 싸다) |

| mean_remove | 0.69 | 5 % | 리덕션 + 빼기 |

np 8 strong 256³ (3.84 ms): tdma_z 2.49 (65 %, 그중 Alltoallv 1.86) — np 8 에서는 §2g 의 통신이 전부. weak np 8(17.0 ms)은 np 1 과 같은 구성 + tdma_z 5.0.

**원인**: FFT 라인 배치가 i(또는 mx) 연속이라 필드(k 연속)·y 배치(jy 연속)와 모두 전치 관계인데, 네 복사 커널이 1차원 스레드 매핑으로 한쪽을 보폭 접근한다 — build_z·scatter_z 에서 두 번 본 그 문제.
`reorder_x_to_y` 는 보폭 쓰기(2 double 씩 Ny 간격)라 이상값(540 MB → 0.6 ms)의 7배.

**다음(제안)**: 네 커널(`pack_rhs_kernel`·`reorder_x_to_y_kernel`·`reorder_y_to_x_kernel`·`scatter_lines_kernel`)을 32×32 공유메모리 타일 전치로. 기대 7.4 → ~2 ms, pressure_solve −40 %, 스텝 −6 %, 비트 동일.
3차원 분할에서 펜슬 전치(all-to-all)가 들어와도 랭크 안의 팩·언팩은 같은 전치 커널이라 버려지지 않는다. build_z 는 PaScaL 이 a·c 를 제자리에서 바꾸므로 매 스텝 다시 조립해야 하고(원본 복사 0.5 ms 와 비슷) 그대로 둔다.
