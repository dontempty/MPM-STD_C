# MPM-STD 재작성 계획 — 2026-10-03

## 0. 한 줄 요약

MPM-STD_C 의 수치는 검증되었지만 **읽기 어렵다.** MPM-STD 는 같은 물리를 **다른 사람이
질문 없이 읽을 수 있는 코드**로 다시 쓴다. 성능 재설계도, 새 물리도 목표가 아니다.
첫 마일스톤은 **app 이 config 를 읽는 것**까지.

## 1. 목표 — "읽기 쉽다"를 측정 가능하게

"읽기 쉬운 코드"는 그대로 두면 아무 제약도 못 한다. 아래 4개를 **합격 기준**으로 고정한다.

### 1.1 합격 기준

| # | 기준 | 측정 방법 |
|---|---|---|
| **R1** | **한 스텝의 데이터 흐름을 `apps/<case>/main.cpp` 하나만 읽고 따라갈 수 있다** | 새 사람에게 main 만 주고 "dt 는 어디서 정해지나 / 온도는 언제 갱신되나"를 물어 답하게 한다 |
| **R2** | **어떤 함수든 그 파일 안에서 무슨 일이 일어나는지 알 수 있다** | 파일-static 가변 상태, 전역 버퍼, 숨은 캐시 **0개** (grep 으로 검사) |
| **R3** | **주석을 전부 지워도 코드가 틀리지 않는다** | 불변식을 주석이 아니라 타입·assert·함수 경계가 강제한다 |
| **R4** | **배열 레이아웃을 질문 없이 이해할 수 있다** | ⚠ 아래 §2 의 실측 반례를 해소했는지로 판정 |

### 1.2 R4 의 근거 — 실제로 측정된 실패

MPM-STD_C 의 배열 레이아웃을 이해하는 데 **같은 질문이 5라운드** 걸렸다 (2026-10-03 세션):

1. "벡터는 면에 저장되고 스칼라는 cell 중심인데 크기가 같다는 게 말이 안 됨"
2. "(4,4) 면 U=(0~6,0~5), V=(0~5,0~6) 이어야 하는데 어떻게 같은 크기인가"
3. "+ 방향 면 하나를 생략하면 CN 2차미분에서 i=6 정보가 필요한데"
4. "rank0/rank1 에서 각각 어디를 푸는 건가"
5. "셀 8개 + ghost 2개면 면이 0~10 인데 배열이 7개여야 하지 않나"

**이것이 이 프로젝트의 존재 이유다.** 코드는 맞았지만 설명 없이는 읽히지 않았다.
원인은 "U/V/W/P/T 가 한 모양을 공유하고, staggering 은 스텐실 인덱싱 관례로만 존재"
라는 규칙이 **코드에 드러나지 않기 때문**이다 (`field_cpu.hpp:19-22` 주석에만 있음).

### 1.3 비목표

- 성능 재설계 (커널 융합, 스트림 오버랩, 통신 숨김) — 나중
- 새 물리 (LES, 다상, 반응) — 안 함
- MPM-STD_C 와의 비트 단위 일치 — **목표 아님.** 수치적 동등성(수렴 차수, 검증 케이스
  통과)만 요구한다. 비트 일치를 목표로 삼으면 읽기 어려운 구조를 그대로 베껴야 한다.
- CPU 만으로의 물리 검증 — §5.3: CPU 는 스모크·단위 테스트까지, **검증 런은 GPU**

## 2. MPM-STD_C 에서 측정된 "읽기 어려움"의 원인 10가지

전수 조사 결과는 `../../MPM-STD_C/Report/study/` 에 있다. 아래는 그중 **구조적 원인**만.

| # | 원인 | 구체 사례 |
|---|---|---|
| **C1** | **주석이 구현과 어긋남 (4건)** | `boundary_ops.hpp:25-28` TDMA fold 설명이 수정 전 버전 / `grid.hpp:29` `dmx` 를 "face-to-face" 라 했지만 실제는 center-to-center / `cuda_stream.hpp:28` "default stream" 인데 새 스트림 생성 / `face_bc.hpp:33` "GPU 로 복사되어 디바이스에서 평가" 인데 실제는 호스트 디코딩 |
| **C2** | **호출 순서 의존성이 주석으로만 강제** | `assemble(=) → buoyancy(+=) → pgrad(−=) → solve`; `zero_dw_lower_wall_face → block_couple_dV → sync(δV) → block_couple_dU`. 어기면 **조용히 틀린다** (Report/27, /30 이 그 기록) |
| **C3** | **같은 수식이 두 곳에 중복, byte-for-byte 일치 요구** | momentum RHS 의 `mAC*/mAP*/mAM*` 와 ADI 의 `emit()`. 주석이 "matches the RHS faces byte-for-byte" 라고 경고 |

| **C5** | **CPU/GPU 분기 전략이 모듈마다 다름 (3종)** | momentum = 진짜 템플릿 / scalar = phantom 템플릿(인자를 안 읽음) / pressure = `shared_ptr<void>` 타입 소거 |

| **C7** | **dead code 가 살아있는 코드처럼 보임** | `momentum_cross_stress_cpu.cpp` 145줄(호출 금지 주석 있음) / `pressure/assemble.hpp` 전체 / `GridDevice` / `cuda_helpers/` 6파일 / 미빌드 TU 6개 |
| **C8** | **할당되고 안 쓰이는 멤버** | GPU `LinearSystem` 의 `rhs_*`/`stage`/`A..D` (랭크당 수십 MB 낭비), scalar GPU 는 워크스페이스 **전체** 미사용 |
| **C9** | **숨은 전역 상태** | `halo_gpu.cu` 의 `g_y_bufs`/`g_z_bufs` 를 **모든 필드가 공유**(동시 호출 불가, 해제 안 됨), 파일-static 디바이스 캐시 다수 |
| **C10** | **조용한 실패** | `get_or` 가 오타 키를 기본값으로 / `face_bc_for` 의 `default: return bc.U` / `parse_int("8e6") → 8` / `cudaMalloc` 반환값 미검사 |

## 3. 설계 규칙

위 10개에 1:1 대응한다. **위반은 리뷰에서 반려.**

| 규칙 | 내용 | 대응 |
|---|---|---|
| **D1** | **주석은 "왜"만 쓴다.** "무엇"은 코드가 말한다. 불변식을 설명하는 주석을 쓰고 싶으면 **대신 assert 나 타입을 쓴다.** 수식 주석은 테스트로 고정한다 | C1 |

| **D3** | **수식은 한 곳에만.** CPU/GPU 공유가 필요하면 `MPMSTD_HD` 헤더 함수 하나로 (MPM-STD_C 의 `scalar_var_stencil.hpp` 가 유일한 성공 사례 — 이것을 **표준**으로) | C3 |
| **D4** | **같은 이름의 `_cpu`/`_gpu` 는 같은 의미여야 한다.** 버퍼·인자·부수효과가 다르면 이름을 다르게 한다 | C4 |

| **D6** | **`void*` 타입 소거 금지.** 헤더 의존이 문제면 전방 선언이 가능한 **클래스**로 만든다 | C6 |
| **D7** | **안 쓰는 코드는 삭제한다.** "나중에 쓸지도"는 git 이 기억한다. 미빌드 파일 금지 | C7 |

### 4.3 equation 내부 구조 (✅ 2026-10-03 확정)

사용자 정의: **"RHS = rhs 를 조립하는 곳, System = 시스템 계수를 만드는 곳.
밖에 solve 함수를 정의하고 안에서 RHS·System 함수들을 호출하여 solve 한다."**

```
equation/<eq>/              (<eq> = scalar, momentum, pressure)
├── rhs/                    RHS 를 조립하는 곳
├── system/                 시스템(삼중대각) 계수를 만드는 곳
└── solve.{hpp,cpp}         바깥의 공개 함수 — 안에서 rhs·system 함수들을 호출해 solve
```

폴더 구조는 사용자가 생성한 그대로 (`RHS`/`System` → 소문자 규칙 적용해 `rhs`/`system`).
`solve` 는 두 폴더 **밖** `equation/<eq>/` 직속이다.

**✅ 결정: 부력·압력구배 같은 외부 물리 항은 main 에서 조립한다** (MPM-STD_C 방식;
solve 캡슐화안 기각 — 2026-10-03). **main 에 물리 구성이 그대로 보이는 쪽**을 택했다.

main 조립을 택했으므로 C2(순서 의존의 조용한 오류) 재발은 다음 두 장치로 막는다:

1. **덮어쓰기(`=`) 공개 함수 금지.** RHS 버퍼는 equation 의 build 함수가 **만들어서
   반환**하고, 외부 항(부력, 압력구배)은 전부 **add(`+=`)만** 한다. 더하기는 가환이므로
   부력·압력구배의 상호 순서는 바꿔도 결과가 같다. (MPM-STD_C 의 순서 의존은
   assemble 이 `=` 로 덮어쓰기 때문에 생긴 것이다)
2. **solve 는 RHS 를 `const` 인자로 받는다.** "RHS 완성 → solve" 순서가 주석이 아니라
   **데이터 흐름**으로 강제된다 (D2 충족).

```cpp
// main — 물리 구성이 다 보이면서도 순서 실수가 어렵다
auto rhs = momentum::convection_diffusion_rhs(fields, properties, dt);  // 버퍼 생성+초기화
buoyancy::add_to(rhs, fields, properties, params, dt);                  // += (가환)
pressure::add_gradient_to(rhs, fields, pressure_acc, dt);               // += (가환)
momentum::solve(fields, rhs, settings, dt);                             // rhs 는 const&
```

### 4.4 빌드 규칙 (✅ 2026-10-03 확정)

**규칙 하나: 실행파일 = `apps/<이름>/main.cpp`.** 그래서 전부 성립한다:

```
make              전체 빌드
make <이름>       개별 앱 빌드 (make rbc, make channel, make test_grid ...)
make test         이름이 test_ 로 시작하는 앱 전부 실행
```

- 앱 폴더의 **모든 .cpp** 가 그 바이너리로 컴파일된다 (main.cpp + 앱 소유 settings.cpp 등)
- `src/` 는 와일드카드 전부 수집 (미빌드 TU 사고 차단) — vendor clone 만 명시적 제외 예정
- 테스트 공용 하네스는 `apps/framework.hpp` (CHECK / CHECK_THROWS_MSG)
- 다른 앱의 소유 코드를 테스트할 때는 그 .cpp 를 include 하는 1줄 TU 를 둔다
  (`apps/test_rbc_settings/rbc_settings.cpp`) — 공용 소비자가 둘이 되면 src/ 로 승격

## 5. 결정이 필요한 갈림길 ★

### 5.1 ★ 배열 모양 — 공유 vs 필드별 (가장 중요)

이 프로젝트의 **중심 결정**이고, §1.2 의 5라운드 질문이 정확히 이 지점이다.

**A안 — 공유 모양** (MPM-STD_C, CaNS 방식)

```
U, V, W, P, T 전부  n_total = n_interior + 2
staggering 은 스텐실 인덱싱 관례로만 존재
면이 셀보다 하나 많다는 사실은 "ghost 슬롯이 흡수 + 한 면은 미저장"으로 숨는다
```

- 장점: halo datatype 1벌, 루프 경계 1종, 컨테이너 균일. **코드가 적다**
- 단점: **§1.2 의 실패가 그대로 재현된다.** 같은 인덱스가 필드마다 다른 위치를 뜻하고,
  벽면 하나는 interior 슬롯·다른 하나는 ghost 슬롯이라 **두 벽이 서로 다른 메커니즘**
  (항등행 교체 vs 명시적 0)으로 처리된다

**B안 — 필드별 모양**

```
U : (nx+1+2h, ny+2h, nz+2h)      ← x 면이 하나 더 많은 것이 할당에 드러남
V : (nx+2h, ny+1+2h, nz+2h)
W : (nx+2h, ny+2h, nz+1+2h)
P,T: (nx+2h, ny+2h, nz+2h)
```

- 장점: **"+1" 이 코드에 보인다.** 질문이 사라진다. 두 벽이 대칭적으로 처리된다
- 단점: halo datatype 이 필드 모양별로 갈라짐(6 → 최대 18), 루프 경계가 필드별,
  `FieldSet` 이 균일 배열이 아님. **코드가 늘어난다**

**C안 — A안 + 관례를 코드로 표현**

```cpp
// 나쁨 (MPM-STD_C): h 가 왜 하단 벽면인지 코드만 봐선 모른다
w[(i*n2+j)*n3 + h] = 0;

// C안: 관례를 이름이 설명한다
for (auto face : grid.lower_wall_faces(Axis::Z)) W[face] = 0;
```

- 장점: A안의 코드량 + 경계 코드의 가독성
- 단점: 핫 커널 안에서는 결국 raw 인덱싱을 쓰므로 **관례가 두 겹**(이름 있는 접근자 +
  raw)이 된다. 부분적 해결

**권고는 B안이었으나 → ✅ 결정: A안 (공유 모양) — 2026-10-03 사용자 확정.**
MPM-STD_C·CaNS 와 같은 선택이다. 코드량·halo datatype·루프 경계가 한 벌로 유지된다.

**A안 선택에 따른 R4 충당 방안** — "+1 이 할당에 드러나는" 길을 포기했으므로,
관례를 다음 세 장치로 코드·문서에 고정한다:

1. **`docs/conventions.md` 를 M4 와 함께 작성** — 이번 세션에서 5라운드 끝에 나온
   그림들(셀/면 번호 대응, "셀 i 는 자기 마이너스 면을 소유", 미지수 범위 = interior,
   스텐실 합집합 = 배열 전체, 랭크 분해 시 면 소유권)을 그대로 옮긴다.
   원본: `../../MPM-STD_C/Report/study/04_mechanisms_and_pitfalls.md` §1, §4
2. **관례 선언을 `field.hpp` 딱 한 곳에** — "U[i] = 셀 i 의 마이너스 x-면 (xf[i])" 를
   타입 주석이 아니라 **명명된 상수/함수로**: `static constexpr Side kFaceSide = Side::Minus;`
   + `int owning_face_index(int cell) { return cell; }` 수준이라도 코드에 존재하게
3. **벽면 특수 처리(하단 벽면 = interior 슬롯, 상단 = ghost 슬롯)는 이름 있는 함수로만
   접근** — `zero_wall_faces(W)` 하나가 양쪽 벽을 다 처리하고, 호출부에 `k=h` 같은
   raw 인덱스가 보이지 않게 한다 (MPM-STD_C 는 이 처리가 3곳에 흩어져 있었다)

## 7. M1 상세 설계 — `config/` (✅ 완료)

> 2026-10-03 추가 결정: 아래 설계의 `Settings`/`load_settings`/`format_settings` 는
> **`apps/rbc/settings.{hpp,cpp}`** 로 이동했다 (§4.1 config 행, 앱별 소유).
> `src/config/` 에는 `ini_parser` + `schema`(바인딩 실행 기계장치)만 남는다.
> 설계 내용 자체(에러 표, 파서 규칙, 테스트 목록)는 전부 유효하며 구현도 동일하다.

### 7.1 MPM-STD_C config 의 구체적 결함 6개

조사 결과 (`ref_01_common_config_boundary.md` §2):

1. **`.toml` 확장자인데 INI 파서** — 배열·인라인 테이블 미지원, 문서화된 함정
2. **`get_or` 가 오타 키를 조용히 기본값으로** — `nmoniter` 가 에러 없이 200
3. **`parse_int("8e6") → 8`** — `strtol` 이 `'e'` 에서 멈추는데 에러로 안 봄.
   double 키에는 `Ra = 1.0e6` 처럼 지수표기를 쓰므로 습관이 옮겨가기 쉽다
4. **주석 제거가 따옴표를 모름** — `dir = "run#1/"` 이 `"run` 으로 잘림
5. **중복 키 조용히 마지막 승**
6. **main 에 `cfg.get<...>("section","key")` 가 50줄** — 키가 문자열이라 오타가
   컴파일에 안 걸린다. 설정 전체 목록을 보려면 main 을 읽어야 한다

### 7.2 설계 — "설정은 타입이다"

핵심 전환: **문자열 키 조회를 main 에서 없앤다.** 모든 설정을 struct 로 선언하고
로더가 한 번에 채운다.

```cpp
// src/config/settings.hpp
namespace mpmstd::config {

struct Mesh    { int    nx = 0, ny = 0, nz = 0; };          // 0 = 미지정 → throw
struct Domain  { double lx = 0, ly = 0, lz = 0; };          // 0 = 미지정 → throw
struct Stretch { bool   uniform_z = true; double gamma_z = 0; };
struct Process { int    npx = 1, npy = 1, npz = 1; };
struct Physics { double rayleigh = 0, prandtl = 0;          // 필수
                 double delta_temperature = 0;              // 0 = 상수물성
                 int    gravity_axis = 2; };
struct Time    { double end_time = 0; double dt_max = 0.02;
                 double max_cfl = 0.3; long max_step = 0; };
struct Output  { std::string stats_dir = "stats/";
                 int    monitor_interval = 100;
                 double stats_start_time = 0, stats_interval = 0; };

struct Settings {
  Mesh mesh;  Domain domain;  Stretch stretch;  Process process;
  Physics physics;  Time time;  Output output;
};

// 파싱 + 검증. 실패는 전부 예외(파일:줄:키 포함).
Settings load_settings(const std::string& path);

// 런 로그용 에코 — 읽은 값 전부를 결정적 순서로 출력.
void print_settings(const Settings&, std::FILE* out);

} // namespace mpmstd::config
```

**이 설계가 해결하는 것**

| 결함 | 해결 |
|---|---|
| 6 (문자열 키 50줄) | **설정 전체 목록이 `settings.hpp` 한 파일에 보인다.** 오타는 컴파일 에러 |
| 2 (조용한 기본값) | 기본값이 **struct 멤버 초기화 한 곳**에 있고, 모르는 키는 throw |
| 1 (이름이 거짓말) | §5.2-a: `.ini` 확장자 |
| 3 (지수표기 절단) | 파서가 **토큰 전체 소비**를 요구 |
| 4 (따옴표 안 주석) | 주석 제거를 **따옴표 인식**으로 |
| 5 (중복 키) | throw |

`Settings` 가 **읽기 쉬움에 직접 기여하는 부분**: R1(main 하나로 흐름 따라가기)에서
main 의 첫 줄이 `const auto settings = load_settings(argv[1]);` 하나로 끝난다.
MPM-STD_C 의 main 은 설정 읽기에 50줄을 썼다.

### 7.4 파서 규칙 (명시)

```ini
; 또는 # 주석 — 단 따옴표 안에서는 주석이 아니다
[section]
key = value          ; 양쪽 공백 제거
path = "has#hash/"   ; 따옴표로 감싸면 안의 # 는 보존, 따옴표는 벗겨짐
```

| 상황 | 동작 |
|---|---|
| `=` 없는 줄 | throw `"<file>:<line>: expected 'key = value', got '<line>'"` |
| 중복 키 | throw `"<file>:<line>: duplicate key 'section.key' (first seen at line N)"` |
| 섹션 선언 전 키 | throw (익명 섹션 금지) |
| 닫히지 않은 따옴표 | throw |
| 모르는 (섹션,키) | throw `"<file>:<line>: unknown key 'section.key'"` ← **D10** |
| 필수 키 누락 | throw `"<file>: missing required key 'mesh.nx'"` |
| `nx = 3.5` | throw `"<file>:<line>: 'mesh.nx' expects an integer, got '3.5'"` |
| `nx = 8e6` | throw (동일) — 토큰 전체 소비 요구 |
| `nx = 0` | throw `"<file>: 'mesh.nx' must be > 0"` (의미 검증) |

**"모르는 키 → throw"의 트레이드오프**: 전방 호환이 깨진다(새 바이너리용 덱을 구
바이너리로 못 돌림). MPM-STD_C 는 warn 을 택했는데, 그건 **이미 조용히 기본값으로
떨어지는 구조를 사후 보완**한 것이다. 처음부터 throw 면 그 구조 자체가 없다.
케이스별 선택 키(예: RBC 전용 `physics.delta_temperature`)는 **해당 앱의 스키마에만
등록**해 해결한다 — 즉 `load_settings` 가 앱별로 "어떤 키를 아는가"를 갖는다.

19. **축별 BC 프레임워크 + de Vahl Davis 2D 열 cavity (2026-10-05 사용자 지시)** —
   "각 축마다 BC 를 선택, Dirichlet·Neumann 커버, 최종 cavity 검증". 입력 `[boundary]`
   (축 kind + `<field>_<axis>_<side>` override; slip 은 override 키워드), 내부
   `boundary::BoundaryCondition` 테이블 하나를 Topology·ghost·ADI fold·압력 변환이
   본다. 2D 는 **ny=1 축 붕괴**(별도 2D 코드 없이 진짜 2D 비용). CPU·GPU 둘 다 구현,
   검증은 CPU 만. 4단계(구조체/로더 → x벽 ghost+fold → x-DCT 압력 → cavity 앱)이며
   단계마다 채널 md5·rbc Nu 비트 일치 게이트. **설계·검증 기록 정본:
   `docs/Design/20261005_boundary_condition_framework.md`** — **4단계 전부 ✅ (2026-10-06)**:
   cavity Ra 1e3~1e6 de Vahl Davis Table V 10항목 ≤0.7% (1e6 Nu_max/min 만 −1.4/−1.0%).
   부산물 교훈 2건: ① 에너지 벽 행 drop 닫기는 dt·κ/dx²≳3 에서 폭주 → `set_wall_closure`,
   ② 접선속도 value ghost 는 1차(벽 마찰 절반) → `[boundary] velocity_ghost = mirror`.

M1 이 끝나면 이 문서에 **"M1 회고"** 절을 추가한다 — R1~R4 기준으로 실제로 읽기
쉬워졌는지, 규칙 D1~D12 중 지키기 어려웠던 것은 무엇인지. 규칙이 현실과 안 맞으면
규칙을 고친다.
